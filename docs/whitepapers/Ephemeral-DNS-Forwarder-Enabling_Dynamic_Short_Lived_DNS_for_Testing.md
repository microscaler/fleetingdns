# FleetingDNS: Enabling Dynamic, Short‑Lived DNS for Testing

## Executive Summary

Modern development teams often struggle to test systems that require dynamic or publicly reachable DNS entries, such as webhooks, OAuth callbacks, TLS endpoints, and multi-tenant applications. Traditional local testing falls short because local environments (e.g. `localhost`) are not accessible to external services, and obtaining public DNS names for ephemeral test instances is cumbersome. The **FleetingDNS** service addresses this gap by providing on-demand, short-lived DNS endpoints that forward traffic to a developer’s local or test environment. In one command, developers can create a temporary public domain name that automatically routes (via a secure tunnel) to their local service. These DNS endpoints exist just long enough for the test (typically 30 minutes), then automatically expire and clean up, reducing overhead and security exposure. This solution enables realistic end-to-end testing of features like OAuth flows, webhooks, and multi-tenant subdomain routing *without* the hassle of manual DNS configuration or long-lived exposures.

In summary, FleetingDNS offers a developer-friendly way to **quickly spin up public DNS addresses bound to local services**, solving the pain of testing scenarios that demand real DNS. It combines dynamic DNS provisioning with secure reverse tunnels, packaged as a simple CLI or SDK. The result is a frictionless testing experience where complex integrations (third-party webhooks, OAuth providers, cross-tenant routing, ACME certificate issuance, etc.) “just work” in a local or CI environment. By automating DNS and tunneling on-demand, this service bridges the gap between isolated development and the connected reality of production systems.

## Problem Definition

### Inadequacy of Current Testing Approaches

Conventional testing tools struggle when an application under test must be reachable via a public hostname or requires SSL/TLS as in production. For example, many OAuth 2.0 providers and third-party APIs require a pre-registered redirect/callback URL that cannot simply be “localhost”. The DNS endpoint of an ephemeral test environment is often not known ahead of time, yet OAuth flows demand static, known callback URLs. This mismatch makes it **difficult to test OAuth and SSO integrations** in ephemeral dev environments or continuous integration (CI) pipelines. Developers have resorted to clunky workarounds like using a fixed set of callback domains or implementing proxy hacks, which adds complexity and isn’t truly representative of production conditions.

Similarly, **webhook integrations** pose a challenge. Services like Stripe, GitHub, or Slack need to POST events to your application, but if you’re developing on a laptop or within a CI container, those environments have no public endpoint by default. Local webhook testing is “challenging” because the development machine isn’t accessible from the internet. The typical solution is to use tunneling tools (e.g. ngrok, Cloudflare Tunnel) that provide a public URL for your local server. However, these often generate random subdomains and require reconfiguration of webhook endpoints every time, unless you pay for static addresses. This friction slows down testing and can lead to missed bugs in event-driven features.

**TLS/HTTPS testing** is another pain point. Browsers and APIs increasingly enforce HTTPS, but obtaining a valid TLS certificate for a local environment is not straightforward. Let’s Encrypt, for instance, will not issue certificates for “localhost” because it’s not a globally unique domain. Developers either use self-signed certs (which cause browser warnings) or skip TLS entirely in dev, risking that certain issues (mixed-content blocking, redirects, cookie scopes, etc.) only surface in production. Testing certificate provisioning (ACME flows) itself is nearly impossible on ephemeral hosts without a public DNS entry. The result is inadequate coverage of TLS-related logic and potential surprises when deploying to production.

Finally, teams building **multi-tenant services with DNS-based routing** (where each tenant has a subdomain, e.g. `tenant1.example.com`, `tenant2.example.com`) face difficulties in QA and dev. Code that dispatches requests based on the request’s hostname can’t be fully exercised with a single `localhost` address. While it’s possible to fake DNS locally (through `/etc/hosts` or wildcard DNS like `*.nip.io` pointing to 127.0.0.1), those approaches only work for the developer’s machine and don’t easily allow external access or realistic domain structures in a shared test environment. In ephemeral test deployments, you might spin up a unique URL per instance, but coordinating DNS for each ephemeral environment is complex. Current techniques either limit testing to one tenant at a time or require manual DNS management, both of which are error-prone.

In summary, **today’s approaches are inadequate** whenever a test scenario demands a *publicly accessible, dynamic hostname*. OAuth flows can’t complete without a known callback domain, webhooks can’t reach your code without a public URL, TLS can’t be fully validated with self-signed certs, and multi-tenant routing can’t be replicated with a single static host. These gaps leave critical integration points either untested or tested in ways that differ from production, risking integration failures and security issues.

## The Solution: Ephemeral DNS Forwarding

**FleetingDNS** solves the above problems by combining on-demand DNS provisioning with transient tunneling. In essence, it gives you a throwaway domain name that automatically channels traffic to your local or test service. Whenever a developer or CI job needs an endpoint, they run a single command (or API call) to provision an **ephemeral DNS endpoint** – for example, something like `https://abc123.testdns.io`. This domain is live and globally reachable, but only for a short window (e.g. 30 minutes). Under the hood, the service ensures any requests to that domain are forwarded through a secure tunnel back to the developer’s machine or container where the application is running.

Crucially, the FleetingDNS handles all the heavy lifting: it interacts with DNS servers to register the new hostname, sets up a **reverse tunnel** connection to the client, and (if needed) provisions SSL so that the domain is accessible via HTTPS. The user doesn’t have to configure DNS records, open firewall ports, or deploy to a public host – the entire process is automated and lasts just long enough for the test to run. After the TTL (time-to-live) expires or the user finishes testing, the domain is reclaimed and the tunnel is closed. This automatic teardown ensures there are no lingering open endpoints. It also enforces that the service is used for **short-lived testing purposes** rather than permanent hosting, which improves security and keeps costs down.

Because each ephemeral domain is unique and randomly generated, collisions are avoided and external services (like OAuth providers or webhook senders) see a “fresh” domain for each test. Yet from the developer’s perspective, it’s extremely simple – essentially **“plug-and-play” public DNS**. For example, if you need to test a Stripe webhook, you could run `ephem-dns forward 8080` and get a URL like `https://stripe-test-<hash>.ephemeraldns.com` which you then paste into Stripe’s webhook settings. Stripe will call that URL, and the FleetingDNS will tunnel the request to your local port 8080. You can run your tests, see the webhook interactions in real time, and when done, the tool will automatically shut down the endpoint. In a CI pipeline, the process might be triggered at the start of an integration test suite and terminated at the end, enabling truly automated end-to-end tests that involve external callbacks.

This solution brings the convenience of cloud-based tunnels (like ngrok) together with the flexibility of dynamic DNS. It essentially provides the benefits of a cloud environment (public addressability, valid TLS, multi-tenant domains) **without requiring you to leave your local dev or ephemeral CI environment**. Everything is ephemeral by design – the DNS entries have very short TTLs and are removed, and the tunnel client has a built-in timeout. This ephemeral nature means minimal cleanup and reduced risk of forgotten open endpoints. By leveraging existing protocols and infrastructure (DNS, SSH/TLS tunnels), the service can be both robust and secure. In effect, FleetingDNS offers **“integration testing as a service”** – you get realistic external connectivity on demand, as easily as running a test case, and it vanishes when no longer needed.

## Core Features

The FleetingDNS service provides a rich set of features tailored for ease of use, reliability, and integration into development workflows:

* **One-Command Endpoint Provisioning:** Developers can spin up an endpoint with a single CLI command or API call. This triggers the creation of a unique subdomain (e.g. `abc123.yourdomain.test`) and configures it to route to a specified local port or service. The process is instantaneous and requires no manual DNS setup. *(For example, with ngrok a single command yields a public URL like `https://<random>.ngrok.io` pointing to your localhost; FleetingDNS provides similar one-step convenience.)*

* **Reverse Tunnel Client (30‑Minute Auto-Expiry):** The service includes a lightweight client that runs on the user’s machine or CI server to establish a reverse tunnel. The tunnel links the ephemeral DNS endpoint to the user’s local server. By default, each tunnel is capped at a **30-minute lifespan** – after which it closes automatically. This ensures ephemeral usage and guards against accidentally leaving tunnels open indefinitely. The time limit is configurable up to certain limits on paid plans (see *Deployment and Monetization*), but all sessions eventually auto-expire to enforce cleanup. The user can, of course, manually terminate earlier as well. Auto-expiry helps prevent misuse and frees up resources, aligning with the “temporary test” use case.

* **DNS TTL Cleanup:** All DNS records created are given a very short TTL (e.g. 60 seconds). When a session ends, the corresponding DNS entry is deleted from the authoritative server. Thanks to the short TTL, any DNS caches out on the internet will drop the record soon after it’s gone. This means the domain won’t linger in resolvers for long, reducing the risk of someone hitting a stale address. The system may also proactively serve a blank response or NXDOMAIN for expired names to accelerate the cleanup. In effect, the service **scrubs its DNS footprint** as soon as domains are no longer in use.

* **HTTP(S) Redirect and Raw Tunnel Modes:** The forwarding can operate in two modes. In **raw tunnel mode**, the service simply pipes traffic from the ephemeral endpoint directly to the local service (akin to a direct TCP proxy). This is ideal for protocols like HTTP APIs, gRPC, etc., and even custom TCP protocols. Alternatively, an **HTTP(S) redirector mode** is available: in this mode the ephemeral endpoint can immediately issue an HTTP 302 redirect to another URL. For example, you might use a redirect if you want the ephemeral domain to send traffic to a different domain or if testing scenarios where the mere presence of a resolvable domain is needed to redirect elsewhere. One use case for the redirect mode is simulating DNS-based **tenant routing**: e.g., any request to `tenantX.ephemeraldns.com` could redirect to `localhost:port/tenantX` or a specific local URL, letting you test host-based routing logic in your app by observing the Host header. Another use of redirect mode is for implementing an OAuth *callback proxy* – the ephemeral domain can catch the OAuth provider’s callback and then redirect (or tunnel) to the actual app callback URL, working around the requirement for pre-registered domains. This mode provides flexibility when a full TCP tunnel isn’t needed or when a simple HTTP redirection is more appropriate.

* **Integration with Test Frameworks (SDKs):** FleetingDNS is designed to slip into automated tests and CI/CD workflows. Client libraries (SDKs) are provided for popular languages like **Python, Go, and JavaScript**, so that tests can programmatically create and destroy ephemeral endpoints. For instance, a Python integration test could call `ephemeraldns.create_endpoint(port=3000)` and receive a hostname that it can use for testing an OAuth flow or webhook. The SDK handles starting the tunnel and ensures cleanup at the end of the test. This allows seamless integration with frameworks like pytest, JUnit, or CI pipelines – tests that were previously hard to automate (due to external callbacks) can now dynamically create the needed infrastructure on the fly. The SDKs mirror the CLI functionality and use the same backend APIs. As an analogy, **ngrok’s agent can be run as an embedded library** in apps or tests, and our service follows that pattern – making ephemeral DNS endpoints available as a building block for automated testing.

Each of these core features is geared toward **developer productivity** and reliability in testing. With one command you get a temporary domain; with auto-expiry and TTL you don’t worry about cleanup; with flexible modes you can adapt to different test scenarios; and with SDK integration you can automate everything. Together, they dramatically reduce the overhead of testing integrations that normally require domain juggling and networking acrobatics.

## Architecture Overview

FleetingDNS’s architecture consists of a few modular components working in concert to provision DNS and tunnel traffic quickly and securely:

**1. Dynamic DNS Service (CoreDNS + Data Store):** At the heart of the system is a DNS server responsible for answering queries for the ephemeral domains. We leverage **CoreDNS** (a flexible, plugin-based DNS server) as our authoritative DNS for a designated domain (say, `*.ephemeraldns.com`). CoreDNS is configured with a **dynamic backend** so that new subdomains can be added/removed on the fly. One option is using CoreDNS’s *etcd plugin* – storing DNS records in an Etcd key-value store that CoreDNS reads from. This approach has been used to achieve dynamic DNS updates, as CoreDNS’s etcd plugin “allows for dynamic DNS by reading the values from etcd”. Alternatively, we can use a Redis-backed plugin (community-developed) for storing records; CoreDNS is very extensible, and in fact a developer was able to create a Redis-backed dynamic DNS plugin in a few hours. In our design, when a new endpoint is requested, a DNS A record (or CNAME record) is written into the store (etcd/Redis), mapping the ephemeral subdomain to the tunnel server’s IP. The TTL is set low (e.g. 60s as noted) for these records. CoreDNS then serves this DNS zone – responding to queries so that external clients can resolve the domain to our server. Because the data store updates in real-time, we can add and remove records without restarting the DNS service. CoreDNS’s efficiency and plugin model make it ideal here, but other DNS implementations or APIs (e.g. dynamic updates via RFC2136, or even cloud DNS providers) could also be used if needed.

**2. Reverse Tunnel Server:** This is the component running on the public side (cloud VM or server) that actually receives traffic for the ephemeral domains and forwards it to the correct client. We support multiple tunneling technologies for flexibility. A straightforward implementation uses **SSH reverse tunnels**: when the client runs the CLI, it essentially opens an SSH connection to the tunnel server (authenticated with a key or one-time token) and sets up a remote port forward. For example, the client might SSH into the server and open port 10000 on the server side that forwards to `localhost:8080` on the client side. The ephemeral DNS name (e.g. `abc123.ephemeraldns.com`) would then resolve to the server’s IP, and the server is configured to forward incoming traffic on that port to the SSH tunnel. Projects like *pgrok* have demonstrated a multi-tenant reverse proxy built on SSH in a similar fashion. Alternatively, for raw TCP tunneling, **socat** (a general-purpose relay tool) could be used to pipe data between the server socket and the client’s connection. Another modern option is **zrok**, which uses an overlay network (OpenZiti) to tunnel traffic; the service could integrate with zrok’s approach to manage tunnels efficiently. In any case, the architecture creates a **persistent outbound connection** from the client to the server, so no inbound ports need to be opened on the user side (this is the same fundamental idea that ngrok uses: the client agent makes an outbound connection, and traffic flows down that pipe). The server is multi-tenant – it can handle many simultaneous tunnels. It distinguishes them by subdomain or port number. For HTTP(S) traffic, a single wildcard TCP listener (e.g. on port 80/443) can inspect the Host header or SNI to route to the correct tunnel. For arbitrary TCP, we may allocate a unique port per tunnel on the server side (and use DNS SRV records or communicate the port via the client). The “reverse tunnel server” thus comprises a connection acceptor and a routing layer that ties requests to the correct client session.

**3. HTTPS Termination and Redirector (Optional):** If the user’s scenario requires HTTPS, the service can provide SSL termination using a wildcard certificate. During deployment, we obtain a wildcard TLS certificate for `*.ephemeraldns.com` (for example) – this covers any subdomain we generate. The server can then terminate TLS for incoming requests on the ephemeral domain, using the wildcard cert, and forward the plaintext traffic through the tunnel to the client’s local service (which may be HTTP). This way, even if the local dev server isn’t running HTTPS, external services see a valid HTTPS endpoint (no certificate errors). We also support end-to-end TLS passthrough when needed (for example, if the local service is running its own TLS or if the protocol isn’t HTTP). The architecture could allow both modes: by default, to make things simple for developers, the server does TLS termination with the wildcard cert and funnels data to the client over the secure tunnel. But if “raw” TLS is desired, we can use SNI routing and not terminate TLS (just route based on SNI name). In addition, an **HTTP redirector** service can run alongside: this component handles the scenario where an ephemeral domain should issue an HTTP 301/302 redirect. In implementation, this is just a small HTTP server that, when it receives a request for a particular ephemeral subdomain, looks up a target and responds with a redirect. For example, if `foo.ephemeraldns.com` is configured in redirect mode to `http://localhost:5000/foo`, the server will send back a 302 pointing to that address (which likely would only be reachable if you’re on the same network or have some VPN – so this mode is primarily for simulating certain behaviors). The redirector component shares the wildcard TLS cert so it can do this over HTTPS as well. Essentially, the redirector gives a lightweight alternative path where full tunneling isn’t needed.

**4. Client Interfaces (CLI and SDK):** On the client side (developer’s machine or CI), the primary piece is the **CLI tool** (or an equivalent library). This client is responsible for: (a) requesting a new ephemeral DNS endpoint from the service (via a REST API or similar call to a control plane), (b) launching and maintaining the tunnel connection, and (c) monitoring the session duration (to enforce the expiry). For instance, a developer might run `ephem-dns forward --subdomain foo 3000`, the CLI calls the service API to create `foo.ephemeraldns.com` (or a random name if none given), then it starts an SSH or WebSocket connection to the server to pipe traffic from port 3000. The CLI will display the assigned URL and remain running until the time limit is hit or the user stops it. Under the hood, the **control plane** could be a simple web service that coordinates DNS record creation and issues credentials or tokens for the tunnel connection. The multi-language SDKs (Python, Go, JS, etc.) wrap this functionality. For example, the Python SDK might start a background thread that runs the tunnel, so that your test can proceed while the tunnel is active, and then it handles cleanup. The CLI and SDK usage correspond to how ngrok provides a CLI and also agent libraries – the idea is to meet developers where they are, whether they prefer command-line tools or integrating capabilities into code.

**5. Coordinating Registry & Cleanup:** There is also a small coordination logic that keeps track of active endpoints, their expiration times, and performs cleanup. This could be as simple as an in-memory registry on the server or a lightweight database. Each time an endpoint is created, an entry is logged (subdomain, user or session ID, start time, etc.). A background job will periodically check for expired sessions to tear down. When a session expires, the system will remove the DNS record from etcd/Redis and signal the tunnel to close. If the client is still connected, it’s informed of expiration (and maybe given a chance to extend if within policy, e.g. a paid user might extend the session). The coordination component also can enforce limits (like one free endpoint at a time, or rate limiting the creation of endpoints to prevent abuse).

The overall architecture is illustrated as follows: A developer requests an ephemeral domain; the control logic creates a DNS entry via CoreDNS+store and assigns a tunnel ID; the developer’s client connects to the tunnel server, which is listening for that ID; external traffic finds the DNS entry via normal DNS resolution and hits the tunnel server (optionally with TLS); the server then uses the ID (subdomain or port mapping) to forward bytes to/from the correct client connection, delivering the traffic to the developer’s service. All of this happens with low latency overhead – essentially just one extra network hop – which is typically acceptable for testing purposes. By using existing technologies (DNS, SSH/TLS) we ensure compatibility and reliability, while the custom glue (coordinator and client) provides the seamless user experience.

## Security Model

Security is a key consideration for FleetingDNS, given that it opens access (albeit temporary) to services running on a developer’s machine or test environment. We outline the current security measures and future enhancements to harden the system:

### Current Protections

The service’s **ephemeral nature and random endpoint generation** serve as first-line security measures. Each tunnel is tied to an unpredictable subdomain (e.g. a GUID or hash in the hostname) which acts as a secret token of sorts – only someone who knows the exact domain can attempt to connect. This is security by obscurity, but when combined with short lifespan, it significantly limits risk. In fact, users of similar tunnel services rely on the hard-to-guess URL as a basic protection, sometimes likened to a password-less secret. If an attacker doesn’t know the ephemeral domain, they cannot target your service; and even if they discover it, the window of opportunity is very small (30 minutes by default, often less by the time they find it).

Additionally, **no inbound ports are opened on the client side** – the tunnel is an *outbound* connection initiated from the developer’s environment. This means the developer’s firewall/NAT does not get exposed; only the cloud server accepts inbound traffic. This architecture inherently reduces the attack surface compared to, say, opening a port in your router for the world. The cloud tunnel server itself is locked down to only accept traffic on necessary ports (80/443 for HTTP/HTTPS, or specific ports for raw tunnels). All communication between client and server occurs over secure channels (SSH or TLS), so the traffic is encrypted in transit over the public internet. This prevents eavesdropping or tampering with the tunnel data. Essentially, FleetingDNS functions like a managed reverse proxy, and it can enforce similar security policies as cloud providers do for their services (rate limiting, connection limits, etc., at the entry point).

We also implement **simple access controls** in the current design: for example, a user can optionally set an HTTP basic-auth username/password on their ephemeral endpoint (the server will then require those credentials on incoming HTTP requests before forwarding). This is analogous to ngrok’s optional protection where you can require a password, adding another layer beyond obscurity. Such a feature is useful if you share an ephemeral URL with a colleague or a test service but want to ensure only authorized parties use it during that session.

Finally, because the service automatically tears down endpoints, it limits the window in which an endpoint could be compromised. Even if an attacker managed to guess or obtain the URL, after expiration the DNS won’t resolve and the tunnel will be gone. The ephemeral DNS names are not reused (or at least not for a long time), so an attacker can’t “wait out” and reuse a known subdomain either. And since each session is isolated, one user’s endpoint does not expose another’s service.

### Future Design Options

While the current model provides basic safety for development use, we have plans for stronger authentication and identity binding to prevent misuse and ensure only intended users can access their tunnels:

* **Client-side SSL Certificates (mTLS):** We are exploring using mutual TLS authentication for the tunnel connections. In this scheme, each authorized user or client would have a unique client certificate. The tunnel server would only accept connections from clients presenting a valid cert signed by our CA. This would ensure that even if someone knew the tunnel parameters, they couldn’t hijack it without the cryptographic credentials. mTLS could also be extended to the edge: for instance, requiring the external party (say a webhook source) to present a client cert might not be feasible (since third-party services won’t have our cert), so our focus is on the tunnel between client and server. Mutual TLS on that link guards against unauthorized clients connecting to the server, and prevents any man-in-the-middle on the control channel. It’s an enhancement over the current SSH key or token approach and can integrate with enterprise certificate management if needed.

* **GitHub-Based Identity Binding:** To make the service developer-friendly yet authenticated, we consider using OAuth integration with platforms like GitHub (or GitLab, etc.) for login and identity. A user would sign up or log in to the FleetingDNS using GitHub OAuth, proving their identity. Then, endpoints they create can be associated with their account. This opens up possibilities like **scoping endpoints to certain user or org** – for instance, one could allow only members of a GitHub organization to access certain ephemeral endpoints (the server could check an OAuth token on incoming requests, though that’s more for protected webhooks scenarios). More concretely, identity binding helps with **audit and abuse prevention** (we know which user created an endpoint, and can track usage) and eventually with features like persistent settings (a user could have default preferences or a reserved subdomain prefix if authenticated). Tying into GitHub also aligns with how many developers work and could simplify the onboarding (no separate account needed beyond an existing GitHub account).

* **Enhanced Endpoint Authentication:** Beyond basic auth or obscurity, we plan to support issuing an **API token or key for each endpoint** that must be present for access. For example, the service could require that inbound requests include a special header (`X-Auth-Token: <random>`) which the developer receives when they create the endpoint. This acts as a one-time password for that endpoint. Any request lacking it is dropped. This way, even if the URL is discovered, without the token the requests won’t go through. This concept, along with IP filtering (allowing the user to specify that only certain source IPs or ranges can access the endpoint), would significantly raise the bar against unauthorized access.

* **Monitoring and Alerts:** On the defensive side, the service will monitor traffic patterns for abuse. In the future, if an endpoint suddenly starts receiving a flood of traffic (which might indicate a DDoS or that the URL got leaked), we can auto-shutdown the tunnel and notify the user. Integration with abuse databases (to block known malicious IPs) and user-defined request limits are also on the roadmap.

### Abuse Prevention

Abuse prevention is critical because a publicly accessible tunnel could be misused (intentionally or not) for spam, phishing, or attacks, which would not only harm victims but also jeopardize the service’s infrastructure (e.g. getting the domain blacklisted). Our approach to mitigating abuse includes both **preventative limits** and **reactive measures**:

* **Session Limits:** Free tier users will be limited in how many concurrent tunnels they can run and how long they last (the 30-minute cap by default). This prevents someone from spawning a large number of endpoints to use as a botnet or long-term hosting. Even paid tiers will have reasonable limits to ensure the service remains for its intended testing purpose (for instance, an Unlimited plan might allow longer sessions or more concurrent tunnels, but with a fair use policy). By capping quantity and duration, we reduce the surface for abuse (it’s hard to run a persistent malicious service on a domain that disappears quickly and can’t easily be mass-created without an account).

* **Authentication & Attribution:** As mentioned, requiring users to log in (with GitHub or other) means we have an identity tied to each endpoint. If abuse is detected from a certain endpoint, we can trace it back to a user and block or ban that user. This accountability itself discourages malicious actors, who prefer anonymous services. Initially, we might allow anonymous usage for the simplest trials (like quick local tests) but with very tight limits; anything beyond that would need login.

* **Content and Traffic Scanning:** While we do not intend to snoop on user traffic (and end-to-end encryption would limit this anyway), the service can perform some automated checks. For HTTP(s) tunnels, for example, the server could look at requested hostnames and paths to flag known phishing patterns (like if someone tries to host a page that looks like a login form to a bank, etc.). Volume-based triggers are easier – if an endpoint is serving an unusual amount of data or numerous different clients are connecting (which is atypical for a dev test, but typical for, say, hosting a public website), that could raise a red flag. In such cases, the service might automatically cut off the tunnel and send an alert to the user asking if that was expected. We will also maintain a report mechanism – if an external party reports an ephemeral domain for malicious activity, we can immediately revoke it and ban the user. The short-lived nature helps here: by the time abuse is noticed, the endpoint might already be gone. But if not, swift termination is possible.

* **Secure Defaults:** The default mode is to be closed and gradually open by choice of the user. For instance, maybe by default an endpoint only accepts GET/POST and common webhook verbs and will reject others unless configured (preventing someone from using it to tunnel an arbitrary protocol for hacking). This might be more of a stretch goal, but highlights that we favor safety first.

In conclusion, the current security model banks on **ephemeral usage and unguessable addresses** to keep things reasonably safe for development scenarios (indeed, many developers use similar tools safely under these conditions). Going forward, we plan to augment this with strong identity and encryption measures (mTLS, OAuth integration) and proactive abuse detection. The aim is to make FleetingDNS not only convenient but also trustworthy for users and safe from becoming a tool for bad actors. It’s a balancing act: we want it open enough for quick testing, but controlled enough to prevent misuse – and our design reflects a layered security approach to achieve that.

## Use Cases

FleetingDNS unlocks a range of use cases across development, testing, and DevOps scenarios. Below are some key scenarios where this service proves especially valuable:

* **CI/CD Pipelines for Integration Testing:** Continuous integration systems can spawn ephemeral test environments (containers or short-lived VMs) to run integration tests. By using FleetingDNS, these environments can obtain a public URL on the fly, allowing external callbacks or multi-service interactions to occur during the test. For example, a CI job running end-to-end tests for an application can create an ephemeral endpoint so that an OAuth provider like Google or GitHub can redirect back to the test environment during the login flow. Similarly, the test environment could receive webhooks from services like Stripe or Twilio to validate end-to-end behavior. Once tests finish (or after 30 minutes), the endpoint disappears. This capability means your CI **truly tests the real integration**, not just stubbing it out, all within an isolated ephemeral context.

* **OAuth and ACME (Let’s Encrypt) Flow Testing:** As discussed, many OAuth 2.0 implementations require a known domain for redirects. With ephemeral domains, developers can test the full authorization code exchange locally or in staging. For instance, a developer can register a placeholder callback like `https://auth-test.ephemeraldns.com/callback` with the OAuth provider and have FleetingDNS use that domain to forward to their local app during test. Even if dynamic, one could leverage the HTTP redirector or a stable proxy domain to bridge the gap. Similarly, **ACME certificate issuance** (from Let’s Encrypt or others) can be tested by using a temporary domain to perform an HTTP-01 challenge. A user could set up an ACME client in test mode to prove they control `temp123.ephemeraldns.com` – the challenge request from Let’s Encrypt’s servers will hit the ephemeral domain and get forwarded to the test ACME client, which responds appropriately. This is particularly useful for DevOps validating auto-cert provisioning in a staging environment. Indeed, developers have resorted to self-hosted tunnels on cheap servers specifically to test Let’s Encrypt HTTP validations; our service makes that process trivial and ephemeral, using a wildcard cert for immediate HTTPS and allowing ACME challenge testing as needed.

* **Isolated Integration Tests and Microservice Interaction:** When working with microservices or components that normally communicate over specific hostnames, you can spin up ephemeral instances of those services with unique routing. For example, suppose you have a multi-service system where Service A needs to call Service B via a DNS name (not just `localhost`). In a local integration test, you could start Service B and use FleetingDNS to give it a temporary name (say `serviceB.testenv.ephemeraldns.com`). Configure Service A (running locally) to call that URL. Now you are testing the real HTTP call flow between services as if they were in a deployed environment, including DNS resolution and possibly HTTPS, all on your laptop or a test container. Once done, the domain goes away, so you can run many such tests in parallel or sequentially without collisions (each test gets a unique domain). This is also useful for testing **network isolation** or firewall rules in staging: you can ensure that only intended ports/protocols are open by seeing how the ephemeral connections behave.

* **Developer Preview and Sharing Environments:** Often a developer wants to share a working preview of a feature branch with a teammate or get quick feedback from a product manager. FleetingDNS allows you to expose your running dev server to the internet in one command, under a benign URL, for a short time. For instance, you could be running a web app on `localhost:3000` and get a URL `myfeature.ephemeraldns.com` that you send to a colleague to try out. This is similar to using ngrok or similar tools for demoing, but our service can make it even more streamlined and tied into your dev tools. Because it supports **custom subdomains (on paid tiers)**, you might even pick a memorable name for the session (if not already taken) to reflect the feature being shown. The ephemeral nature ensures that after the demo, the app isn’t unintentionally left exposed. Furthermore, if your app is multi-tenant and uses subdomains, you could even simulate multiple tenant URLs via multiple ephemeral endpoints at once – giving a realistic preview environment.

* **Education, Hackathons, and Temporary Environments:** In educational settings or hackathons, participants often need to quickly expose their application to others (for example, a webhook from a hardware device, or an external API callback). FleetingDNS provides a quick way for many people to get a public endpoint without dealing with firewall or cloud deployments. Each participant’s usage is isolated under their own ephemeral subdomain. The 30-minute (or adjustable) limit is usually plenty for demonstrations or debugging sessions. After that, if they still need it, they can re-run the command to get a fresh endpoint, ensuring the service resources are recycled. This use case emphasizes **ease-of-use** – since participants might not be infrastructure experts, a one-command solution is ideal.

In all these scenarios, the common theme is that ephemeral DNS + tunneling removes the friction that normally hampers testing and sharing of in-development systems. It empowers developers and test automation to treat *real DNS and network interactions* as part of the normal dev/test cycle, rather than something only tackled in staging or production. The result is higher confidence in integrations and faster iteration when building features that depend on external interactions.

## Deployment and Monetization

For the FleetingDNS service to be sustainable and widely available, we’ve considered both the technical deployment requirements and a pricing model that can support ongoing operation. Here we outline how the service can be deployed (especially as a Minimum Viable Product) and a strategy for monetization via tiered plans.

### MVP Hosting Requirements

One of the advantages of this service is that it can be run with relatively modest infrastructure, especially in the early stages. The key components to host are the DNS server, the tunnel server, and the coordinator API. In an MVP setup, these can all run on a single virtual machine. Providers like **Hetzner Cloud** offer affordable VMs that are well-suited for this use case. For example, a basic VM (\~2 vCPU, 2-4 GB RAM) costing on the order of €3-5 per month can be sufficient to start. Such a machine can easily handle dozens of simultaneous tunnels (if not more), given that most dev/test traffic is sporadic and low-bandwidth.

The VM would run CoreDNS (with etcd or Redis if needed, which are lightweight for our scale) to serve DNS for our domain. It would also run the tunnel service (which could be a custom Go server, an SSH daemon configured for tunnel use, or a containerized solution like zrok’s server). Lastly, a small web service for control (user authentication, API to request new endpoints) would be running. These components can all be containerized for easy deployment.

A critical piece for deployment is obtaining a **Wildcard SSL Certificate** for the domain. During MVP, we can use Let’s Encrypt’s wildcard certificate issuance via DNS-01 challenge (since we control the DNS zone with CoreDNS, we can fulfill the challenge easily by adding a TXT record). This gives us a free, automated wildcard cert for `*.ourdomain.com`. Alternatively, a wildcard certificate could be purchased from a CA if needed, but Let’s Encrypt should suffice and renewals can be automated. Having this wildcard cert means we can terminate TLS for any subdomain. In the MVP, we might decide to terminate TLS at the server (offloading from user’s local) to simplify things.

**Bandwidth and Data Transfer:** We anticipate that tunnels will carry a moderate amount of data (mostly API calls, webhook payloads, maybe the occasional web page for preview). A Hetzner VM includes a generous bandwidth allotment (often 20 TB or more per month) which is more than enough for early usage. We will monitor usage; if some users start transferring very large amounts (e.g. streaming video through a tunnel), that might be curtailed by policy in the free tier. But for typical dev scenarios, bandwidth on a single VM is not a limiting factor initially. We should also consider the network quality: a data center with low latency and good routes to common API providers (AWS, cloud services) will improve the responsiveness of our tunnels. Europe-based Hetzner covers EU well; we might deploy another VM in the US to reduce latency for US-based developers (and handle DNS geo-routing, or let users choose a region).

**Scalability and Redundancy:** For MVP, a single server might be fine. If it fails, being an MVP, some sessions would drop – which is acceptable in a testing context. As we grow, we’d introduce multiple servers for redundancy and to serve different geographic regions. CoreDNS can be replicated or use a highly available store (etcd cluster). The design allows scaling horizontally by simply adding more tunnel servers and delegating subdomains or using anycast DNS for distribution. However, these complexities can wait until we have more demand.

In summary, the MVP can be run on a shoestring budget: one cloud VM, an automated certificate, and standard open-source software. This low cost of operation is encouraging because it means even a few paying users could cover the expenses.

### Pricing Tiers and Sustainability

To maintain the service and continue developing it, we propose a **freemium pricing model** with three tiers: Free, Supporter, and Unlimited (or Pro). The goals are to allow broad adoption via a useful free tier, while offering paid options that unlock more usage or convenience for power users – thereby funding the service.

* **Free Tier:** The free tier is aimed at individual developers casually using the service or evaluating it. It would include the core functionality: one ephemeral endpoint at a time, 30-minute session limit, and perhaps a modest number of sessions per day. The free tier might only allow subdomains that are randomly generated (no custom names) and possibly enforce a short cooldown between uses to prevent abuse. Despite these limits, the free tier should be fully functional for basic needs (e.g. testing a webhook or doing a quick demo). This encourages adoption and word-of-mouth. We’d need to ensure the free usage is not so generous that it jeopardizes resources, but not so restrictive that it’s useless. A possible limit is e.g. 5 sessions per day, one at a time, which is plenty for sporadic development tests.

* **Supporter Tier (Paid):** This tier, perhaps a low monthly fee (e.g. \$5-10/month), is for developers who find the service valuable and want higher limits. Supporter tier could increase the session duration (say up to 2 hours or more), allow perhaps 2-3 concurrent endpoints (for those testing multiple things or multi-tenant cases), and might let the user choose a subdomain name instead of a random one (so it’s easier to remember or align with a project). We might also include priority support or slightly higher bandwidth allocation. The key idea is that for a small fee, a developer or a small team gets a more comfortable experience – fewer interruptions from expirations and the ability to run longer-lived preview environments. Some cosmetic perks like a “supporter” badge in the UI or early access to new features could also be included.

* **Unlimited/Pro Tier:** A higher-priced plan (perhaps \$25-50/month, similar to ngrok’s pro pricing) for heavy users or teams. This would lift most limits: allow essentially unlimited session duration (within reason – maybe we still auto-restart tunnels after 24h to refresh DNS, but seamlessly), allow multiple concurrent tunnels (5 or more, or even an account-wide pool), and crucially **custom domain support**. Custom domain delegation means a user on this tier can use their own domain name with the service. For example, they could CNAME `dev.mycompany.com` to our service and we will provision subdomains under that for them. This is important for enterprise users who want to test under a domain that resembles production (or who have whitelisted domains). We’d also offer stronger security features here by default: e.g. the ability to enforce mTLS on their tunnels, or use IP allowlists. Essentially, the Pro tier is for organizations or advanced developers who need the service integrated into daily workflows and possibly into CI pipelines heavily. This tier’s pricing should reflect the value of convenience and the resources used (longer running tunnels). It could be per user or potentially a small team license.

We should also consider a usage-based component for some aspects – for example, charging a small amount for data beyond a high threshold (to prevent someone from using a Pro account to serve a huge amount of traffic). But given our focus is testing, high data usage is not common, so a flat monthly might be fine.

**Sustainable Funding:** By having the Supporter and Pro tiers, we aim to cover the operational costs and fund development. The free tier serves as marketing and onboarding. If the service truly solves developers’ problems, converting a fraction of users to paid should be achievable. We’d follow the model of many developer tools where free is generous but time-limited or capacity-limited, and those who depend on it daily will see value in upgrading.

Another aspect of sustainability is ensuring we’re not underpricing. The service potentially saves developers significant time and headache (think of the hours spent configuring test DNS, or the risk of a bug due to not testing something properly). Framing the Pro tier as something that could be expensed by a company or justified in a team budget will help. For individuals, the Supporter tier should feel like a “patron” contribution: not very expensive, but showing love for a tool they like, in exchange for some perks.

Operationally, as usage grows, we’d invest in more infrastructure (perhaps running in multiple regions). The cost will scale roughly with active tunnels and DNS queries. DNS queries could spike when many ephemeral domains are in play, but still should be manageable (and CoreDNS is efficient; plus ephemeral nature means not all are active at once). We might integrate with a cloud DNS provider if needed for scalability (like route53 or Cloudflare DNS for our domain), but that also comes with cost – something we’d weigh once usage is high.

Finally, **self-funding** via the above tiers means we likely don’t need heavy external funding to run this as a service. The subscription revenue can pay for servers and development time, making it a sustainable dev-tool SaaS. We could also offer enterprise deals (self-hosted version licensing or higher SLA) if there’s demand, but that’s beyond the scope of initial plans.

To summarize, deployment of FleetingDNS is cheap enough to start lean (a single €3-5 VM, a wildcard cert, open-source components). Monetization via Free/Supporter/Pro tiers ensures hobbyists can use it free while power users contribute to costs. With just a handful of Pro users, we’d cover the server bills; anything beyond that can fund new features and possibly a small team to maintain the service. This model follows the footsteps of similar services (ngrok’s free vs paid plans, etc.) and aims for a fair balance between community utility and business viability.

## Future Enhancements

Looking ahead, we have a roadmap of features and enhancements to make FleetingDNS even more powerful, secure, and convenient:

* **Mutual TLS (mTLS) for Tunnel Authentication:** Building on the idea of client-side certificates from the security model, we plan to implement mTLS handshakes for establishing tunnels. The server will require the client’s identity to be verified by a client certificate. This provides strong assurance that only authorized clients (e.g. your CI pipeline or your laptop with the cert installed) can create and maintain tunnels, eliminating the risk of rogue clients. In practical terms, we might have a command to generate a client cert for a user (or they upload their public key/cert to their account), and the tunnel server trusts those. mTLS could also be extended to the edge for special cases: e.g., a user could enable that any inbound connection to their endpoint must itself present a certificate (this could be used in high-security testing, though it’s not common for third-party webhooks to do so). At minimum, mTLS on the tunnel ensures encryption and authentication at the transport level, complementing application-level security.

* **Integration with GitHub/GitLab (DevOps workflows):** We aim to tightly integrate FleetingDNS into existing developer platforms. For example, a GitHub Action could automatically create an ephemeral endpoint when running certain workflows, and perhaps post the URL as a status check or comment on a Pull Request for reviewers to test the deployed preview. We could provide a GitHub App or Action that simplifies this. Similarly, GitLab CI or Bitbucket pipelines can use our CLI or a native integration to expose review apps. Beyond CI, integration could involve tying domain creation to repository events – e.g., whenever a developer opens a PR, a unique subdomain could spin up for that PR’s environment (if using something like Kubernetes preview environments, we connect to that). On the OAuth side, integration with GitHub might allow mapping a user’s GitHub team membership to allowed usage of the service (for enterprise scenarios). The idea is to make ephemeral environments a first-class concept in the developer’s toolchain, with our service as the plumbing behind it. In addition, logging in via GitHub (OAuth) as mentioned will make it easy to manage one’s endpoints on a dashboard, revoke them, see logs, etc., all tied to their Git identity.

* **Custom Domain Delegation:** A highly requested feature (especially for a paid tier) is the ability for users to bring their own domain name. In the future, a user could point a wildcard CNAME or NS record from their domain (say `*.dev.mycompany.com`) to our service. Then, when they create endpoints, instead of using our default domain, it uses a subdomain of `dev.mycompany.com`. This is great for testing in environments where the domain name itself has significance (some apps treat cookies or CORS differently based on domain, etc.), or for white-labeling the service in an organization. We’ve seen analogous features in similar products – for example, zrok recently added custom domain support for their tunnels. Implementing this securely means isolating each customer’s domain mapping and potentially issuing SSL certificates for them (via Let’s Encrypt or by letting them upload certs). It’s an advanced feature, but one that can differentiate our service for professional use. We might start with a simpler version: allowing the user to specify a custom subdomain prefix on our domain (like choosing a name rather than random). But full custom domain (where the domain is completely theirs) is the ultimate goal.

* **Longer and Persistent Tunnels (with Usage Dashboard):** While ephemeral by nature, we might add a mode for **persisting an endpoint** for a longer period (for example, a staging environment that is always up). This would effectively blur the line between “ephemeral test” and “semi-permanent dev environment.” To support this, we’d implement features like automatic renewal of endpoints, the ability to turn an ephemeral session into a saved one (maybe a reserved subdomain that always routes to your machine when online). A dashboard could show which endpoints are active, allow users to manually expire them or extend them, and provide metrics (like how many requests went through, any errors, etc.). This moves towards a more productized solution beyond just CLI. It’s in the future scope since our initial focus is short-lived sessions, but user feedback might drive us to offer persistent tunnels as an option.

* **Edge Functions or Response Inspection:** This is more speculative, but we could allow minor processing at the server side for testing purposes. For instance, a user might enable an “inspect mode” where the service logs incoming requests and responses (similar to how ngrok’s web interface lets you see request dumps). This could help debugging webhooks without needing additional tools. We could also allow simple rules like mocking a response or redirecting certain paths differently. Essentially, the tunnel server could evolve into a programmable test proxy. However, this would be an advanced feature and possibly beyond a whitepaper scope – it’s a possible future direction if we wanted to offer more than basic forwarding.

* **Improved CLI/UX Features:** We plan to continuously improve the user experience. Ideas include: auto-detecting the local service (so you can just run `ephem-dns` without specifying port, if there’s e.g. a common config or using something like `dev.yaml` to know what to expose), integration with local development servers (maybe a plugin for frameworks to auto expose when in dev mode), and better error messages (like if a tunnel can’t be created due to network issues). We also will look into cross-platform support (ensuring the client works on Windows, Linux, Mac seamlessly, maybe even in web browsers via WASM for some use cases).

In conclusion, the future enhancements aim to make FleetingDNS more **secure, integrated, and flexible**. Features like mTLS and OAuth integration will bolster security and manageability, while custom domains and CI toolchain integration will make the service fit naturally into professional development workflows. We envision a future where setting up an ephemeral test URL is as routine as running unit tests – and our roadmap is geared to making that future a reality with continual improvements to the service’s capabilities. Each enhancement will be developed with the same principle as the core service: making developers’ lives easier when it comes to testing the hard things.

With these planned enhancements, FleetingDNS can evolve from a handy testing utility into an indispensable part of the DevOps toolkit for modern, cloud-native development – all while maintaining the simplicity and developer-centric design that is key to its adoption.
